# Jira Server MCP

Локальный MCP-сервер для Jira Server 7.13.18. Он работает через `stdio`,
обращается к Jira REST API v2 и авторизованным URI содержимого вложений, которые
возвращает сама Jira. Все запросы выполняются от имени пользователя, указанного в
локальном конфигурационном файле.

Сервер не использует Browser Use, Atlassian Rovo и административные Jira API.

## Возможности

| MCP-инструмент           | Назначение                                                                        | Запись                  |
| ------------------------ | --------------------------------------------------------------------------------- | ----------------------- |
| `jira_get_current_user`  | Текущая учётная запись Jira                                                       | Нет                     |
| `jira_search_issues`     | Поиск по JQL; JQL по умолчанию — `assignee = currentUser() ORDER BY updated DESC` | Нет                     |
| `jira_get_issue`         | Основные данные задачи                                                            | Нет                     |
| `jira_get_transitions`   | Доступные текущему пользователю переходы и поля transition screen                 | Нет                     |
| `jira_get_attachments`   | Список вложений задачи с ID и метаданными                                         | Нет                     |
| `jira_get_attachment`    | Содержимое вложения по ID с Basic Auth                                            | Нет                     |
| `jira_get_linked_issues` | Входящие и исходящие связи с другими задачами                                     | Нет                     |
| `jira_transition_issue`  | Preview или выполнение перехода по ID                                             | Да, после подтверждения |
| `jira_add_comment`       | Preview или добавление комментария                                                | Да, после подтверждения |

После перехода сервер повторно получает задачу и сравнивает фактический статус с
целевым. После добавления комментария сервер получает созданный комментарий по
его точному ID и проверяет текст.

## Стек

- Node.js 20 или новее;
- TypeScript в строгом режиме;
- официальный MCP TypeScript SDK v2;
- Zod для проверки конфигурации и аргументов инструментов;
- Vitest, ESLint и Prettier для проверок.

В рантайме нет фреймворка веб-сервера: транспорт MCP — локальный `stdio`, а к Jira
выполняются HTTPS-запросы встроенным в Node.js `fetch`.

## Установка

```bash
cd /path/to/jira-mcp
npm ci
npm run build
npm run check
```

Сборка создаётся в `build/`. Тесты не обращаются к рабочей Jira и используют
локальные заглушки HTTP/MCP.

## Конфигурация

По вашему решению логин и пароль хранятся в JSON-файле открытым текстом. Файл не
следует добавлять в Git, пересылать или помещать в синхронизируемую папку. Сервер
откажется запускаться, если файл доступен группе или другим пользователям.

Создайте закрытую конфигурацию из примера:

```bash
mkdir -p "$HOME/.config/jira-mcp"
chmod 700 "$HOME/.config/jira-mcp"
install -m 600 config.example.json "$HOME/.config/jira-mcp/config.json"
```

Откройте `~/.config/jira-mcp/config.json` в редакторе и замените значения
`username` и `password`. Не вводите пароль в командной строке: так он может
попасть в историю shell.

```json
{
  "jira": {
    "baseUrl": "https://jira.onlinepatent.ru",
    "auth": {
      "type": "basic",
      "username": "your-jira-login",
      "password": "your-jira-password"
    },
    "timeoutMs": 15000,
    "previewTtlMs": 300000,
    "maxAttachmentBytes": 10485760
  }
}
```

`baseUrl` обязан использовать HTTPS. Допускается Jira с context path, например
`https://example.org/jira`. Значения по умолчанию: тайм-аут 15 секунд, срок
действия preview-токена 5 минут и максимальный размер загружаемого вложения 10
MiB. `maxAttachmentBytes` можно увеличить максимум до 50 MiB, учитывая, что MCP
передаёт бинарные данные в base64 и использует дополнительную память.

Если корпоративный сертификат Jira подписан внутренним центром сертификации,
запускающему Codex процессу можно передать путь к PEM-сертификату через стандартную
переменную Node.js `NODE_EXTRA_CA_CERTS`.

## Подключение к Codex

Команда ниже вычисляет абсолютные пути при регистрации сервера:

```bash
cd /path/to/jira-mcp
NODE_BIN="$(command -v node)"
codex mcp add jira-local -- "$NODE_BIN" "$PWD/build/index.js" --config "$HOME/.config/jira-mcp/config.json"
codex mcp list
```

Если Codex уже был открыт, после регистрации перезапустите его или начните новую
задачу. Сервер пишет MCP-протокол только в `stdout`; диагностические сообщения
идут в `stderr`.

Для локального запуска без Codex:

```bash
npm run build
node build/index.js --config "$HOME/.config/jira-mcp/config.json"
```

При таком запуске процесс ожидает MCP-сообщения в `stdin`, поэтому отсутствие
обычного текстового приглашения — нормальное поведение.

## Вложения и связанные задачи

Чтобы проанализировать вложения без браузерной сессии, сначала вызовите
`jira_get_attachments` с ключом задачи. Инструмент вернёт ID, имя, MIME-тип, размер
и автора каждого доступного вложения. Затем передайте нужный ID в
`jira_get_attachment`. PNG, JPEG и другие изображения возвращаются как MCP image
content; остальные файлы — как embedded resource.

Обе операции выполняются с той же Basic Auth, что и REST API. Сервер принимает URI
содержимого только с настроенного Jira origin и только по известным Jira-путям
вложений. Redirect отключены. Если вместо изображения Jira вернёт HTML-страницу
входа, MIME-проверка завершит вызов безопасной ошибкой и браузер не будет запущен.

`jira_get_linked_issues` возвращает обычные Jira issue links в обоих направлениях:
`direction`, отображаемое отношение `relationship`, тип связи и ключ второй
задачи. Этот ключ можно сразу передать в `jira_get_issue`,
`jira_get_transitions`, `jira_get_attachments`, переход или комментарий. Создание
и удаление связей намеренно не предоставляется.

## Preview и подтверждение записи

Операции чтения выполняются сразу. Запись всегда состоит из двух отдельных
вызовов:

1. MCP вызывает инструмент с `confirm=false` и параметрами операции.
2. Сервер проверяет задачу и возвращает preview и одноразовый `previewToken`.
3. Codex показывает preview пользователю и ждёт явного согласия.
4. После согласия MCP повторно вызывает этот же инструмент с `confirm=true` и
   полученным `previewToken`.
5. Сервер расходует токен, выполняет ровно одну запись и проверяет результат через
   Jira API.

Токен связан с ключом задачи, transition ID, полями или текстом комментария. Его
нельзя использовать повторно. Для перехода сервер также проверяет, что статус
задачи не изменился между preview и подтверждением. Если у transition screen есть
обязательные поля, preview перечислит их и не выдаст токен, пока значения не будут
переданы в `fields`.

После успешной записи с неуспешной проверкой сервер возвращает `executed=true` и
`verified=false`. Он намеренно не повторяет запись автоматически: это защищает от
двойного перехода или комментария при временной ошибке чтения.

## Проверка на тестовой задаче

После подключения можно последовательно попросить Codex:

1. `Покажи, под какой учётной записью подключена Jira.`
2. `Найди мои задачи в Jira через assignee = currentUser().`
3. `Покажи доступные переходы для TEST-123.`
4. `Покажи вложения TEST-123 и открой PNG-вложение по возвращённому ID.`
5. `Покажи связанные задачи TEST-123 и данные первой связанной задачи.`
6. `Подготовь перевод TEST-123 по transition ID 31, но пока не выполняй.`
7. После проверки preview: `Подтверждаю переход.`
8. `Подготовь комментарий "MCP smoke test" в TEST-123, но пока не добавляй.`
9. После проверки preview: `Подтверждаю добавление комментария.`

Замените `TEST-123` и `31` на тестовую задачу и один из ID, возвращённых
`jira_get_transitions`. У пользователя должны быть обычные права Jira на просмотр,
переход и комментирование этой задачи.

## Ошибки и безопасность

- `401` преобразуется в ошибку аутентификации; блокировка Jira CAPTCHA определяется
  отдельно по `X-Seraph-LoginReason`;
- `403`, `404` и `5xx` возвращаются как безопасные структурированные ошибки;
- тайм-ауты, сетевые сбои и невалидный JSON обрабатываются без вывода тела
  внутреннего исключения пользователю;
- автоматические HTTP redirect отключены, а клиент разрешает только пути
  `/rest/api/2/...` и проверенные attachment content URI на настроенном Jira
  origin;
- размер вложения проверяется по `Content-Length` и фактически прочитанным байтам,
  а MIME-тип сверяется с метаданными Jira;
- заголовок `Authorization` и пароль не журналируются;
- конфигурация должна быть обычным файлом с правами `600`;
- сервер не предоставляет административных инструментов.

Basic Auth изолирован за интерфейсом `AuthProvider`. Для будущего перехода на
OAuth 1.0a Jira-клиент и MCP-инструменты менять не потребуется: достаточно
реализовать новый провайдер подписи запросов и расширить схему конфигурации.
